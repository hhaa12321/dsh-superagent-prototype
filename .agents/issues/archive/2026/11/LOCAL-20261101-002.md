## Body

## Background / Problem
The fork can be used as the working repository for a real dsh-superagent installation. The minimum bootstrap loop must prove that the running agent can receive a request from its own GitHub fork, prepare an isolated worktree, and produce a reviewable branch or pull request without disturbing existing DSH profiles.

## Goal
Install and configure the repository as an isolated `superagent` DSH profile, point it at `hhaa12321/dsh-superagent-prototype`, and verify one controlled self-development work item end to end.

## Acceptance Criteria
- [ ] `superagent` is a separate DSH profile on port 3082 with a dedicated absolute state directory; existing profiles are unchanged.
- [ ] The source uses the fork and a GitHub CLI identity that can read and push to it.
- [ ] Policy allows only the intended GitHub identity for the initial loop.
- [ ] The executor prepare command validates repository context and creates one isolated worktree per Ticket.
- [ ] Service status has no setup problem and the expected Source is active.
- [ ] A controlled issue mention creates a Ticket and an agent-produced branch or pull request targeting the fork.
- [ ] Delivery records the isolation and rollback boundaries visibly.

## Planned Validation
- Compare profile files before and after setup.
- Confirm port 3082 is owned by the isolated profile.
- Read settings back from the Management API.
- Exercise a controlled mention and inspect Ticket, worker output, branch/PR, and service logs.
- Run the repository checks on any self-produced code change.

## Risks / Boundaries
- Do not touch or recreate `web`, `dsh-tui`, `headless`, or `open-design`.
- The current operator GitHub account and agent account are the same; this proves the loop, not production credential isolation.
- Do not weaken policy, select personal Sessions, or enable Feishu, auto-merge, webhooks, Gitee, or multi-repository support in this task.
- Do not claim self-modification if only installation/configuration is proven.
