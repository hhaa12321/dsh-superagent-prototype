# LOCAL-20261101-003: Make GitHub ticket execution repository-binding aware

## Body

## Background / Problem
The prototype is globally bound to one GitHub repository. Repository identity is absent from Source instances, domain records, worker execution, cursors, health, policy, and pull lifecycle, so a second repository would collide or overwrite the first.

## Goal
Deliver the first Phase 1 vertical slice: one configured GitHub RepositoryBinding drives the complete existing Issue -> Ticket -> worker -> PR path, while repository identity is persisted and propagated through Source, Thread, Ticket, workspace, and tools. Remove the old global-repository schema and configuration path rather than adding compatibility.

## Acceptance Criteria
- [ ] A RepositoryBinding records provider, immutable provider repository ID, slug, URL, credential reference, and enabled state.
- [ ] Source instances have stable instance IDs independent of Source kind and resolve through a RepositoryBinding.
- [ ] Trigger, Thread, Ticket, health/cursor, workspace, and worker tool context use the binding rather than a global repository.
- [ ] Fresh persistence schema contains repository identity and rejects old state directories explicitly; no migration, fallback, or dual-read path remains.
- [ ] One configured GitHub repository remains fully functional end to end.
- [ ] Tests prove identical native issue/PR numbers from two fake repositories cannot share Thread, Ticket, workspace, cursors, health, or PR binding.
- [ ] Tests prove accepted Tickets and resumed Tickets retain their repository binding.
- [ ] `pnpm check` passes.

## Planned Validation
- Focused unit/integration tests for repository identity and collision isolation.
- Full `pnpm check` typecheck, test, and builds.
- Inspect persisted SQLite rows and generated worker environment for repository identity and secret isolation.

## Risks / Boundaries
- Clean break: no migration of old settings, cursors, domain rows, or generated environments.
- No Gitee adapter, webhooks, automatic repository discovery, auto-merge, per-binding scheduler rollout, or plugin marketplace in this slice.
- Do not weaken the existing self-authored-event safety rule.
- Keep changes within the current GitHub execution path; do not build unused provider abstractions before a second forge exists.
